# Jino Backup Manager

Карточка БД имеет выбор строк и групповые операции, размеры последних проверенных копий (не всех версий/частей), отдельные дату скачивания и дату снимка. Расписание принимает один db_alias или список db_aliases, валидирует всю группу и сохраняет атомарно. Совпадающие по next_at/every_hours БД планируются одним заданием с устойчивым schedule_occurrence и атомарным продвижением группы. Пользователь подтвердил последний доступный существующий снимок Jino, без создания свежего снимка. Настройки реальным клиентам самостоятельно не включать. docs/40_database_catalog_and_bulk_schedules.md, тесты: 362 passed, 1 skipped и 21 JS; визуальные тесты scripts/check_database_card.py только синтетические. Перед установкой backend проверить текущие задания; сохранять ключи и части.

Клик по названию сервера в таблице открывает полную карточку (#server/<row>); клик по неинтерактивной части строки переключает только правый блок. Кнопки и поля строки не должны открывать карточку. Статическое изменение применяется без перезапуска исполнителя; scripts/check_activity_ui.py проверяет 1440/1000/800/390.

Актуальная оптимизация FTPS описана в docs/39_ftp_performance_fixes.md: до пяти файловых заданий, общий ConnectionBudget(10) выдаёт фактические сеансы, полного резерва ftp_connections в планировщике нет. SFTP/HTTPS-файлы удерживают по одному слоту того же бюджета. Простаивающий FTPS-сеанс освобождается при наличии ожидающего; занятые передачи не прерываются. Новые записанные артефакты проверяются отдельным работником по потоковому хешу, результат ждёт проверок; старые done сохраняют две проверки источника. Счётчики checkpoint инкрементальные; пустые и повторные фиксации смещения устранены, fsync перед подтверждением данных сохранён. Контекст обхода и явные ошибки CWD/PWD/MLST/MLSD не снижают число файловых потоков, RETR сохраняет адаптацию. Метаданные пока последовательны, префикс части после обрыва перечитывается. Полный прогон 359 passed, 1 skipped. Протокол установки — .state/ftp-performance-deployment.json. Перед следующими живыми действиями проверяй фактическое состояние, сохраняй ключи и части.

В UI прежние ошибки скрываются из текущих предупреждений после фактического старта нового задания того же типа (started_at/first_started_at), включая его последующее завершение. Файлы и БД независимы; очередь без старта не отменяет прежний результат. Свежая диагностика последнего задания сохраняется даже при совпадении кода со старым (API дописывает её после исторических записей). Отдельная Проверка панели не скрывается. Это только статическое отображение, отчёты/журналы/API не очищаются; перезапуск и новые входы не нужны. Подробности — docs/37_superseded_errors.md.

Управляемый FTPS разделяет очереди новых/частичных и готовых (`done`) файлов. Один дополнительный работник на задание проверяет готовые копии без файлового FTPS-сеанса; общий семафор ConnectionBudget допускает один локальный SHA-256 готовой копии на весь исполнитель. Две проверки источника выполняются через MetadataSession с меньшим приоритетом, отмена/пауза — между блоками по 1 МиБ. Готовые файлы не блокируют ограниченную очередь передач/обход, завершение ждёт всех проверок. Прогресс дополнен local_verifications и pending_verifications; active_transfers — только передатчики. Диск и метаданные остаются общими, лимиты заданий прежние, SFTP/HTTPS/CLI не изменены. Полный прогон 352 passed, 1 skipped. Подробности — docs/36_parallel_verification.md; протокол установки — .state/parallel-verification-deployment.json. Перед любыми дальнейшими действиями проверь фактическое состояние.

С 14 ноября по запросу пользователя управляемые FTPS/SFTP-задания пропускают явно известные ссылки и специальные объекты без перехода по ним. `REMOTE_TYPE_UNSUPPORTED` записывается в FILE_SKIPPED, files.skipped и files.errors; результат PARTIAL. Неизвестные типы остаются REMOTE_TYPE_UNSAFE, пути и коллизии проверяются строго. Отдельный низкоуровневый skip_unsupported_types по умолчанию False, управляемый runner включает его независимо от skip_unsupported_names. HTTPS, CLI и архивный workflow не расширены. Полный прогон: 348 passed, 1 skipped. Подробности — docs/35_skip_special_objects.md. Перед продолжением любых живых задач проверь их фактическое состояние; сохраняй прежний ключ и части.

По указанию пользователя от 13 ноября временные файловые отказы после исчерпания пяти операционных переподключений автоматически возвращаются в SCHEDULED/AUTO_RESUME_WAIT с тем же ключом и частями. Задержки 5/15/30/60 минут, подтверждённый рост байтов сбрасывает задержку; общий срок 24 часа отсчитывается по first_started_at и не сбрасывается автоматическими попытками. После перезапуска последняя прерванная файловая работа тоже может автоматически вернуться в план. Это заменяет прежнее требование ручного продолжения для сетевых файловых сбоев и WORKER_RESTARTED. БД, ручные PAUSED/STOPPED, блокировки, смена привязки, ошибки сертификатов/TLS, доступа, путей и целостности не повторяются автоматически. Не создавай новый ключ ради автоматического повтора. Срок/причина видны в карточке, попытки — в журнале. Подробнее `docs/34_automatic_file_resume.md`; протокол `.state/auto-resume-deployment.json`. Перед новым действием проверяй актуальные состояния.

С 13 ноября FTPS stat использует точечный MLST после CWD/PWD с проверкой корня, имени, размера и времени; при неподдерживаемой команде или недостаточных фактах — прежний строгий MLSD. Управляемый ParallelCollector не дублирует две проверки нового файла, уже выполняемые checkpoint; готовая копия всё равно проверяется до и после локальной верификации. В progress есть metadata_mlst_checks, metadata_listing_checks и processed_files текущего запуска. FILE_VERIFY означает проверку готовой копии; график учитывает её как работу с файлами, но не как новые загруженные байты. Применение сохранено в `.state/metadata-deployment.json`, 22 прежних ключа без новых заданий. На трёх серверах подтверждены MLST и 451 обработанный файл за контрольные 95 с, при почти нулевых новых байтах; семь повторов CWD/MLST сохранились, устранение всех обрывов не подтверждено. Полный прогон 318 passed, 1 skipped. Подробности — `docs/33_ftps_metadata_hot_path.md`. Перед следующими действиями проверяй актуальное состояние.

## Назначение и текущее состояние

Сервис для разового и планового резервного копирования сайтов клиентов с хостинга Джино (Jino.ru). Копия должна содержать файлы сайта, актуальные дампы всех связанных БД, манифест и результаты проверок; храниться в зашифрованном виде вне Jino.

В проекте есть спецификация `docs/`, Python-прототип в `src/jino_backup/`, CLI `backupctl`, локальная браузерная панель и тесты `tests/`. Реализованы импорт, отдельное шифрованное хранилище секретов, архивный workflow, прямой MySQL и интервальное расписание, обычные копии, управляемая очередь с карточками, приоритетом и отдельными файловыми/БД-заданиями. FTPS скачивает во время обхода через PycURL: 2–5 сеансов на сервер, общий предел 10; очередь выполняет до пяти файловых в бюджете 10 сеансов и одного БД-задания; FTPS/SFTP независимы от БД, HTTPS-файлы последовательны с БД одного сервера. Первоначальные 54 FTP-отказа — исторический результат, позднее CA-цепочка исправлена и подтверждены работающие FTPS-передачи. Панельный пилот дал 3 проверенных БД, а последующий массовый проход — 7 `DB_ONLY`, 53 SQL и 1 035 файлов. Это не подтверждает завершение всех файловых копий. Автоматическое создание снимка приложением, панельный экспорт в архивном `auto`, S3/Object Lock, retention, внешние уведомления и тест запуска восстановленного приложения не реализованы. Текущие команды — `README.md`, карта документов и исторических этапов — `docs/README.md`, результаты последних изменений — `docs/22_parallel_ftps.md`–`docs/25_documentation_review.md`. Не описывай запланированные компоненты как реализованные. Общайся и веди документацию на русском языке; идентификаторы кода — на английском.

## Архитектура и порядок разработки

- Реализованный стек: Python 3.11+, SQLite, `cryptography`, CLI; `paramiko` — необязательная зависимость для SFTP. Для нового развёртывания рекомендован Python 3.12+. PostgreSQL и Playwright остаются ориентирами для следующих этапов.
- Пользователь выбрал локальное хранение. Для массового скачивания явно выбраны обычные файлы в `F:\jino`, отдельные папки серверов и запусков: команда `backup download-servers ... --execute --plaintext`. Проверка TLS остаётся обязательной. Архивный режим отдельно использует `settings set-backup-dir`; в этой рабочей папке он настроен на `C:\Projects\backup\backups`. Не добавляй S3 как обязательное условие работы.
- С 11 ноября пользователь требует именовать папки серверов **по логину**, не по служебному номеру. Используется `login` из исходной записи, при отсутствии — `ftp_login`; дубли уточняются FTP-хостом. Уже перенесены 54 папки, содержимое всех 168 исходных файлов сверено по SHA-256. Для новых выгрузок файлов и БД используется единая папка той же записи. Логины остаются только в локальных путях, не в публичных отчётах. Подробности — `docs/12_login_folder_names.md`. Служебные ID и ключи заданий менять не нужно.
- После первого пилота пользователь 11 ноября прямо поручил «выгружай все доступные сервера». Разрешены штатный вход в однозначные панельные аккаунты предоставленного JSON, чтение файлов и экспорт доступных существующих MySQL-снимков, с сохранением обычных файлов в `F:\jino`. Проход `all-available-2026-11-11` закончил очередь, `finished: true`, итог 7 `DB_ONLY`, 47 `FAILED`, 53 проверенных SQL и 1 035 проверенных файлов. Для 34 аккаунтов требуется CAPTCHA, повторные входы автоматически не запускаются. PID и пути прежнего запуска — `.state/active-download.json`, итоговый отчёт — `F:\jino\jino-all-724256b48ae48e4a06acd5da.json`, подробности — `docs/13_all_accounts_download.md`. Перед любым новым запуском проверь фактическое состояние процесса. Строки 1 и 53 остаются неоднозначными. Удаление, восстановление и обход MFA/CAPTCHA не разрешены. Не повторяй уже отправленные операции без проверки фактического результата.
- Разделяй оркестратор, реестр сайтов, провайдер секретов, адаптеры панели/передачи файлов/БД/хранилища, проверку артефактов и уведомления. Бизнес-решения выполняются детерминированным кодом.
- Начинай с локального безопасного исследования структуры импорта и тестов на искусственных данных; затем реализуй файловый MVP, полный бэкап, расписание и эксплуатационные функции. Реализована локальная браузерная панель `backupctl ui` на `127.0.0.1:8765`: общий прогресс, карточки и журналы серверов, отдельные файловые и БД-задания с паузой/продолжением/остановкой, изменение каталога, очередь с порядком, временем начала и приоритетом. Удаление записи сохраняет копии. Исходный JSON не изменяется, новые секреты хранятся отдельно в шифрованном vault. Прогресс читается из дописываемых JSONL и read-only SQLite. Во время работы исполнителя не открывай содержимое заменяемых JSON/ENC ради опроса панели, это может блокировать `os.replace` на Windows. Источники и контракты описаны в `docs/14_local_dashboard.md` и `docs/15_management_and_work_plan.md`.
- В управляемой очереди `backupctl ui` БД, HTTPS-файлы и проверки доступа используют общий допуск: один новый вход в час, максимум три за скользящие три часа, CAPTCHA блокирует следующие входы до действия оператора. FTPS/SFTP независимы от этого допуска. Самостоятельные CLI-команды старого массового прохода и экспорта новым допуском пока не охвачены. Не запускай их параллельно с управляемой очередью. Прежние частичные HTTPS-файлы и журнал SQL продолжаются только для неизменённой исходной привязки и подходящей даты; выбранный ключ сохраняется в задаче. После перезапуска выполнявшиеся задачи получают `INTERRUPTED` и требуют ручного продолжения, будущая очередь сохраняется.
- Для БД в `auto` выбирай разрешённый доступный метод: снимок панели, прямой экспорт БД или SSH. Одноразовый PHP-экспортёр требует отдельного запроса; универсальный веб-шелл недопустим.
- Сохраняй контракты CLI `backupctl`, сущностей и `manifest.json` из спецификации. При обоснованном изменении синхронно обновляй документацию.

## Обязательные инварианты

- В таблице с 12 ноября показывается общий прогресс последних заданий файлов и БД с равным весом, без процента отдельного файла. Файлы учитываются по байтам всего дерева после инвентаризации, БД — по числу проверенных дампов; неизвестный объём остаётся неопределённым, `PARTIAL` не выдаётся за100%. На телефоне прогресс виден перед управлением. Доработка статических ресурсов проверена без перезапуска исполнителя; подробности и границы — `docs/23_server_table_progress.md`.

- С 12 ноября управляемый FTPS использует PycURL и очередь файлов во время обхода. Пользователь согласовал `ftp_connections` 2–5 на сервер, default 3; лимит включает один сеанс метаданных. Общий `ConnectionBudget` ограничен 10 слотами исполнителя, текущие файлы показаны отдельно, при обрывах уменьшается число новых передач. SFTP/HTTPS и БД используют прежние исполнители. Сеансов больше, но задание одного сайта остаётся единственным. Продолжены прежние задания строк 1 и 38 без дублей; перед следующим запуском проверь состояние. У строки 1 причиной прежнего отказа оказалась одна некорректная UTF-8-запись среди 86 элементов конкретного каталога. При разрешённом пропуске имён она отражается как `INVALID_UTF8_NAME` с escape-представлением, корректные файлы продолжаются. Строгие проверки путей и TLS сохранены. Фактическая архитектура, тесты и границы доказательств — `docs/22_parallel_ftps.md`.

- `COMPLETE` означает наличие всех обязательных файлов и БД, успешную проверку артефактов и чтения копии во внешнем хранилище. Отсутствие дампа БД — `FILES_ONLY`, отсутствие файлов — `DB_ONLY`; устаревший снимок нельзя выдавать за свежий.
- Учитывай время исходного снимка отдельно от времени скачивания. Для несинхронизированного экспорта живых файлов и БД указывай `BEST_EFFORT`. Успешный бэкап и успешный тест восстановления — разные результаты.
- Проверяй явную привязку клиента, сайта, корня файлов, аккаунта панели и всех БД. Панельный аккаунт и FTP-профиль — отдельные сущности; совпадение паролей или хоста не доказывает соответствия.
- Не допускай одновременных заданий одного вида для одного сайта. По указанию пользователя от 12 ноября FTPS/SFTP и БД одного сайта разрешены одновременно; HTTPS-файлы и БД последовательны. Учитывай `idempotency_key`, ограничивай тайм-ауты, повторы и нагрузку на аккаунт; перед повтором действия панели проверяй его фактический результат.
- Используй FTPS/SFTP с проверкой TLS/host key, не отключай проверку сертификатов и не переходи молча на plaintext FTP. Не выходи за разрешённый корень, в том числе через символические ссылки.
- FTPS с 11 ноября использует явный CA-набор Mozilla `certifi`: Windows выбирала истёкший промежуточный сертификат, хотя сертификат самого Jino действовал. После исправления на строках 2, 3 и 4 подтверждены вход, MLSD и чтение небольшого файла через TLS 1.3 с проверкой имени. Полные деревья и остальные профили повторно не проверялись. Jino документирует явный FTPS21 и SFTP2222 с FTP-доступами; SSH22 — отдельная услуга. SFTP-рукопожатия на трёх хостах прошли, но без сверенного host key пароли не отправлялись. Подробности — `docs/16_ftps_protocol_diagnostics.md`; не выдавай первоначальную общую ошибку TLS за неисправность действующего серверного сертификата.
- С 12 ноября старый `source: FTP` в `diagnostics` явно помечается в UI как история первого прохода. При более новом управляемом FTPS-результате он скрывается в таблице и её фильтре причин, но сохраняется в карточке; новые ошибки TLS не скрываются. API и отчёты не изменены. На момент проверки было 21 прежнее TLS-отклонение, 19 исторических меток осталось в таблице; строки 1 и 38 продолжали обход. Исправление статических ресурсов применено без остановки заданий и без новых проверок аккаунтов. Подробности — `docs/20_historical_ftp_diagnostics.md`.
- По отдельному разрешению пользователя в управляемой очереди включён по умолчанию `skip_unsupported_names`: настройка сохраняется для каждого сервера и доступна на вкладке файлов. Пропускаются Windows-несовместимые имена; каталог — вместе с поддеревом. Структурные пути, управляющие символы и выход за корень остаются фатальными. Пропуски пишутся как `FILE_SKIPPED` в приватные события и `files.skipped`/`files.errors` манифеста, результат — `PARTIAL`. Журнал имеет отдельный фильтр пропусков до LIMIT500. CLI и архивный workflow по умолчанию остаются строгими. Продолжение неактивного задания подхватывает текущую настройку сервера; новую массовую работу ради смены этой настройки не запускай. Подробности — `docs/18_skip_unsupported_names.md`.
- Изменение UI панели приводит к `UI_CHANGED` и остановке адаптера. MFA/CAPTCHA передаются оператору без обхода.
- Backup workflow не восстанавливает данные поверх production, не меняет DNS и не выполняет платежи. Тест восстановления проводится в изолированном окружении.
- Закрывай соединения и сессии, очищай созданные заданием временные объекты при успехе, ошибке и отмене. Не удаляй чужие файлы или предыдущие копии. Ошибки очистки фиксируй явно.
- В явно выбранном режиме обычных файлов `.jino-progress` и подтверждённые части сохраняются намеренно для продолжения после перезапуска. Они содержат клиентские данные, не являются временными объектами обычного архивного задания и не должны автоматически удаляться после сетевого сбоя.
- Файловая передача использует первую попытку и пять переподключений через 2/4/8/16/32 секунды для временных сбоев отдельной операции. Повтор каталога сохраняет остальной обход в памяти; постоянного кэша инвентаризации нет. `RETRY_WAIT`/`RECONNECT`/`RETRY_EXHAUSTED` видны в журнале и UI. «Продолжить» возобновляет прежний ключ и части, в том числе после `PARTIAL`. До пяти файловых заданий в бюджете 10 сеансов и одного БД-задания одновременно (при 3 сеансах — три сервера). FTPS/SFTP и БД одного сервера независимы; HTTPS-файлы и БД одного сервера последовательны. Пауза сохраняет слот. После обновления продолжены прежние FTPS-задания строк 1 и 38; перед любым следующим запуском проверь их фактическое состояние и не создавай дубль. Живой обход уже восстановился после повторных обрывов, завершение копий ещё не подтверждено. Подробности — `docs/19_recovery_and_server_navigation.md`.
- Текущее прямое указание пользователя для интеграционного теста выгрузки БД: **ничего пока не удалять**. Серверные SQL, локальные дампы и неудачные части теста сохраняются; `backup export-jino-db` по умолчанию использует `KEEP_REMOTE`. Это исключение к штатной очистке выше. Операции удаления на предоставленных ресурсах сейчас не разрешены.
- Копии хранятся вне административного контура Jino; ключи шифрования отделены от данных. Ежедневный исполнитель не получает права удаления старых версий; retention и обслуживание выполняются отдельно.

## Секретные исходные данные

Повторы больших файлов уточнены 12 ноября: управляемый параллельный FTPS сбрасывает счётчик пяти переподключений только при росте подтверждённого смещения своего файла. Застой по-прежнему ограничен 2/4/8/16/32 секундами, срок задания — 24 часа. Журнал сохраняет безопасные числовые коды libcurl, классификацию и продвижение, без исходного текста исключения. Старые CLI и обход каталогов сохраняют прежний лимит. Обновление восстановило два активных и 20 ожидающих заданий без новых ключей; строка 1 оставалась в очереди, строка 7 продолжалась. В строке 7 пойман `RETR` / libcurl 18 (преждевременное завершение потока); подтверждено автоматическое продолжение с 8 461 975 552 до 8 503 918 592 байт без остановки задания. Виновник закрытия потока не установлен; исторические ошибки строки 1 числового кода не имеют. Перед любым следующим действием проверь фактическое состояние. Подробности — `docs/24_large_file_recovery.md`.

Текущая доработка списка FTP от 12 ноября описана в `docs/21_ftp_listing_errors_and_logs.md`: постоянные FTP-коды, повреждённый список и UTF-8 различаются; приватный журнал сохраняет каталог, операцию и числовой ответ, а карточка имеет отдельный фильтр ошибок каталогов. При `continue_on_error` отказ подкаталога даёт `PARTIAL`; корень и строгий режим остаются фатальными. Точная причина прежнего отказа строки 1 после 3 857 каталогов не сохранилась. После установки продолжены прежние задания строк 1 и 38 без дублей; перед любым новым запуском проверь их состояние.

- `abw_sibds__server.json`, экспорты FileZilla, конфигурации CMS, дампы БД, cookies, HAR и состояние авторизации считай секретными. Не печатай их содержимое в терминал, логи, ответы, документацию или тестовые fixtures; не коммить их.
- Для исследования JSON выводи только структуру: имена полей, типы, количества, доли пустых значений и обезличенные ошибки. Не раскрывай значения строк. Не считай base64 шифрованием и не пытайся использовать необратимый хэш как пароль.
- При импорте выбирай точную таблицу `abw_sibds__server`, используй явную карту полей и `dry-run` по умолчанию. Неоднозначные привязки требуют проверки оператора.
- В приложении храни ссылки `secret_ref`; значения передавай в защищённое хранилище. Не передавай секреты в аргументах команд или URL.
- Наличие файла с доступами и разрешение на импорт сами по себе не разрешают вход во все клиентские аккаунты. Для живых проверок нужен явно разрешённый аккаунт и объём действий.
- Используй только синтетические или тщательно обезличенные тестовые данные. Не удаляй и не перемещай оригиналы секретных файлов без соответствующего задания.

## Проверка изменений

Для панельного адаптера установите extra `panel`; синтетический браузерный тест использует установленный Chrome. Последний полный прогон — 292 теста прошли, 1 нативный MySQL-тест пропущен, 48,26 с; затем 57 затронутых тестов прошли после уточнения фильтрации диагностических полей. Управление через Chrome проверено при ширинах 1440, 1000, 800 и 390; переключатель пропуска и отдельный журнал дополнительно проверены на 1440/390. Восстановление, кнопки продолжения и выбор карточки проверены на 1440/390. Синтетический FTPS-тест использует отдельный локальный TLS-сервер и проверяет защищённую передачу, отказ недоверенному CA и неверному имени. После исправления CA-хранилища живые FTPS-проверки прошли на трёх профилях. Живые команды и границы доказательств описаны в `docs/11_database_export_integration.md`, `docs/12_login_folder_names.md`, `docs/13_all_accounts_download.md`, `docs/14_local_dashboard.md`, `docs/15_management_and_work_plan.md`, `docs/16_ftps_protocol_diagnostics.md`, `docs/18_skip_unsupported_names.md`, `docs/19_recovery_and_server_navigation.md`, `docs/22_parallel_ftps.md` и `docs/24_large_file_recovery.md`. Они выполняются отдельно от обычного pytest.

Установка: `python -m venv .venv`, затем `.venv\Scripts\python.exe -m pip install -e ".[dev]"`. CLI: `.venv\Scripts\backupctl.exe --help`. Тесты: создайте `.test-tmp`, затем `.venv\Scripts\python.exe -m pytest -q --basetemp .test-tmp/validation`. Pytest очищает выбранный `--basetemp`; используйте только отдельные тестовые каталоги. Для необязательного теста отдельного нативного MySQL-сервера установите `JINO_RUN_NATIVE_MYSQL_TEST=1`; нужны `mysqld`, `mysql`, `mysqldump` в PATH. Существующие службы и БД этот тест не использует. Команды и ограничения описаны в `README.md` и `docs/09_local_validation.md`.

Для реализации проверяй затронутые контракты и сценарии из `docs/07_tests_and_roadmap.md`. Особенно важны: отсутствие ложного `COMPLETE`, утечки секретов, неверного сопоставления аккаунтов, повторного запуска операций, выхода за корень, а также обработка обрыва передачи, повреждённых артефактов и отмены. Локальные тесты не должны зависеть от реальных клиентских доступов. Живые интеграционные проверки запускай отдельно на разрешённом тестовом аккаунте.

В отчёте указывай результат изменений, выполненные проверки и оставшиеся ограничения. Документация, мок или тестовый fixture не подтверждают работоспособность интеграции с реальным Jino.
