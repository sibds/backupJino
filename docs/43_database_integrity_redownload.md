# Повторное скачивание дампа после DB_INTEGRITY_FAILED

По указанию пользователя от 15 ноября управляемое БД-задание после `DB_INTEGRITY_FAILED` автоматически ставится на повторное скачивание. Сохраняются ID задачи, ключ workflow, выбранные БД, исходный снимок и подтверждённые остальные SQL. Общее правило ручного продолжения БД после иных отказов этим исключением не отменяется. Самостоятельные CLI не получают новый автоматический диспетчер.

## Очередь и пределы

Допускаются **три дополнительных попытки**, минимальные задержки — 5, 15 и 60 минут. Фактическая дата учитывает общий допуск Jino: один новый вход в час, не более трёх за скользящие три часа. CAPTCHA/MFA не обходятся. Действуют прежние сериализация БД и запрет дубля того же вида на сервере.

В задаче сохраняются `db_redownload_count`, `db_redownload_exhausted`, `scheduled_at`, `next_at`, `last_attempt_result`. Повтор получает состояние `SCHEDULED` и этап `DB_REDOWNLOAD_WAIT`; если допуск недоступен, исполнитель переводит его в прежний `WAITING_RATE_LIMIT` либо `WAITING_OPERATOR`. Счётчик не сбрасывается от роста байтов: постоянно некорректный серверный SQL не вызывает бесконечную очередь.

Пауза/остановка пользователя, блокировка, удаление и смена привязки не обходятся автоматикой. При исчерпании трёх попыток задача остаётся ошибочной, файл сохраняется. После исправления причины явное «Продолжить» открывает новый бюджет попыток с тем же ключом. Ожидающий повтор переживает перезапуск без изменения даты и без дополнительной попытки. Восстановление уже выполнявшегося прерванного БД-задания сохраняет прежнее требование ручного продолжения.

После запуска новой версии автоматически рассматриваются только последние управляемые БД-задания с этой ошибкой и неизменённой разрешённой привязкой. Исторические ошибки входа/панели и ранний массовый CLI не повторяются.

## Сохранение повреждённой версии

Для `KEEP_REMOTE` каждая загрузка получает отдельную принадлежащую workflow часть. Непрошедшая проверку часть остаётся на диске; она не считается проверенным дампом. При следующем проходе уже проверенные БД не скачиваются снова. Чужие серверные SQL не присваиваются и не удаляются.

Если повреждён итоговый локальный SQL известного workflow, он остаётся под прежним именем, пока новый кандидат не скачан и не прошёл проверку. В зашифрованном журнале сохраняется подпись заменяемого файла. Перед заменой она проверяется снова: изменение оператором во время скачивания приводит к `LOCAL_DESTINATION_CONFLICT`, а не перезаписи. Замена выполняется через атомарный `replace_with_retry` после проверки структуры, размера и SHA-256; результат повторно читается и проверяется. Старые неудачные части сохраняются для аудита, их массовая очистка не добавлена.

Сбой между записью кандидата, финальным переименованием и фиксацией журнала восстанавливается через `pending_artifact`. Повреждённый объект исключён из списка `validation=PASS` и количества подтверждённых дампов. Сохраняются результаты остальных исправных SQL; `DB_ONLY` не выдаётся до выполнения всех проверок выбранной области.

## Серверный файл и кэш

Повтор скачивает известный принадлежащий workflow серверный SQL. Перед ним заново запрашиваются готовность и размер этого же файла. Изменение пути отклоняется; повторное создание экспорта для уже заказанной БД не отправляется. Ещё не обработанные БД того же задания продолжают обычный workflow с первоначальным экспортом по необходимости.

Проверка ранее сохранённого кэша при повреждении SQL возвращает `DB_INTEGRITY_FAILED` и безопасную ссылку на его журнал. Управляемый исполнитель сохраняет её как `db_repair_job_id`, пропускает повторное использование повреждённого кэша и возобновляет исходный журнал. Обычные проверки аккаунта, снимка, выходной папки и выбранной области остаются обязательными; несовпадение не разрешает расширить доступ или присвоить чужой файл. Внутренний `resume_job_id` не является новой командой CLI.

Если неверен сам серверный SQL, повторная передача не исправляет его содержимое: после трёх отказов нужна проверка источника оператором. Новый снимок Jino автоматически не создаётся. Проверка SQL не означает выполненный тест восстановления приложения.

## Периодические правила

Правило плана не отключается на первом `DB_INTEGRITY_FAILED`: оно ждёт завершения отдельного бюджета повторов. После исчерпания сохраняется прежняя остановка постоянного отказа. Задание, которое ещё завершает обработку ошибки, продолжает занимать свой слот: план и расписания конкретных БД не создают параллельную работу в этом промежутке.

## Проверки

Полный прогон перед заключительным согласованием с расписаниями: **404 passed, 1 skipped**, 99,70 с. Финальные проверки очереди, правил и экспорта — **101 passed**, 36,48 с; JS-регрессии — **22 passed**. Целевые сценарии включают сохранение битой части, неудачную/успешную замену итогового файла, неизменность числа экспортов, обновление размера известного серверного SQL, повреждение кэша и возобновление его журнала, ограничение повторов, паузу/остановку, сохранение даты после перезапуска и отсутствие ложного PASS.

Синтетические данные: `tests/test_database_redownload.py`, `tests/test_panel_export.py`, `tests/test_account_batch.py`, `tests/test_dashboard_management.py`, `tests/test_work_plan.py`. Команда: `.venv/Scripts/python.exe -m pytest -q tests/test_database_redownload.py tests/test_work_plan.py tests/test_dashboard_management.py tests/test_panel_export.py tests/test_account_batch.py --basetemp .test-tmp/db-redownload-ready`.

## Установка

`.state/db-redownload-deployment.json`, фаза `RESTORED`: восстановлены пять активных файловых и 20 ожидающих работ, сохранены 25 ID прежней очереди. Проверены все 58 ID реестра и две ручные остановки. Четыре последних допустимых БД-отказа автоматически получили `SCHEDULED / DB_REDOWNLOAD_WAIT`, попытка 1 из 3; новых задач и новых ключей не создано. Ещё один исторический отказ не повторён: для этого сервера уже есть более новое БД-задание в очереди. Дата допуска сохранена с учётом политики панели. Это подтверждает постановку повторов, а не уже состоявшееся успешное скачивание каждого повреждённого SQL.
