# Требования к Jino Backup Manager

Это целевые требования. Фактические возможности и ограничения на 12 ноября 2026 года перечислены в [README](../README.md) и [обзоре документации](25_documentation_review.md); уведомления, retention и восстановление приложения ещё не реализованы.

## Назначение

Сервис обеспечивает независимые от хостинга проверяемые резервные копии сайтов клиентов. Пользователь может запустить копирование одного сайта или группы сайтов, получить результат и закрыть сеанс. Позднее подключается расписание.

Цель не ограничивается скачиванием файлов. Для сайта с БД резервная копия считается полной, только если сохранены файлы, актуальный дамп **всех связанных БД**, метаданные и доказательства проверки.

## Границы MVP

**Включено:** управление профилями, импорт JSON-дампа с доступами панели и XML FileZilla, FTPS/SFTP, экспорты БД, внешнее хранилище, манифест, SHA-256, статусы, журнал и оповещения.

**Не включено:** изменение DNS, перенос сайта на другой хостинг, резервирование почтовых ящиков без отдельного задания, платежи Jino, обход CAPTCHA/MFA, массовое восстановление на production, выполнение произвольных команд через загружаемый PHP-код.

## Пользовательские сценарии

1. Оператор выбирает сайт, нажимает «Создать копию», получает `job_id`, отслеживает статус и скачивает отчёт.
2. Оператор выбирает несколько сайтов и запускает последовательную или ограниченно параллельную обработку.
3. По расписанию сервис сохраняет копии и уведомляет только о проблемах, новых рисках и результатах согласно политике.
4. При недоступной панели используется заранее согласованный альтернативный способ получения БД.
5. Если БД недоступна, система сохраняет доступные файлы и **отдельно** сообщает, что восстановления полного сайта такая копия не гарантирует.
6. Администратор восстанавливает копию в изолированном окружении и фиксирует результат проверки.

## Нефункциональные требования

- **Безопасность:** никаких отключений TLS-проверки, небезопасного логирования паролей, автоматического обхода MFA/CAPTCHA, загрузки универсальных веб-шеллов.
- **Ограничение влияния:** работа только в разрешённых каталогах, чтение данных по умолчанию, отсутствие восстановления поверх работающего сайта, не более одного задания на сайт одновременно.
- **Повторяемость:** сбойный запуск можно повторить с тем же `idempotency_key` без создания ложного успешного результата.
- **Наблюдаемость:** лог содержит `client_id`, `site_id`, `job_id`, этап, длительность, объём, код ошибки, но не секреты и содержимое клиентских данных.
- **Масштаб:** управляемая очередь ограничена двумя заданиями на разных серверах, одним заданием на сервер; для FTPS согласованы 2–5 сеансов на сервер (по умолчанию 3, включая метаданные) и общий предел 10. [Реализованный ограничитель и границы](22_parallel_ftps.md).
- **Совместимость:** сайты с PHP/MySQL как базовый вариант; PostgreSQL как адаптер с отдельной проверкой; иные CMS/хостинги через расширения.
- **Восстанавливаемость:** наличие архива без успешной проверки/тестового восстановления не является достаточным доказательством работоспособности.

## Предлагаемые цели эксплуатации

| Параметр | Исходная настройка | Примечание |
| --- | --- | --- |
| Ручной запуск | По требованию | Основной сценарий MVP |
| Плановый запуск | Раз в сутки | Только после согласования политики с клиентом |
| Уведомление об ошибке | До 15 минут после завершения | Целевой SLO, не гарантия хостинга |
| Ежедневные версии | 14 дней | Изменяемая политика |
| Недельные версии | 8 недель | Изменяемая политика |
| Месячные версии | 12 месяцев | Изменяемая политика |
| RPO/RTO | Задаются по клиенту | После замера размеров, частоты изменений и времени восстановления |

## Определение готовности MVP

На контрольных сайтах продемонстрированы: полный бэкап при доступной панели, корректный `FILES_ONLY` без доступа к БД, обработка большого файлового дерева, восстановление из внешней копии в тестовом окружении и отсутствие секретов в логах.
