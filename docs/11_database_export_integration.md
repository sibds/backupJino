# Интеграционная проверка панельной выгрузки БД

## Задание и правила проверки

Пользователь запросил тестирование выгрузки дампов на предоставленных ресурсах **с использованием приложения** и подробное документирование действий. Проверка начинается с ранее согласованного аккаунта — первой однозначной записи панельного импорта, строки 2 исходного JSON. В предыдущем пилоте в этом аккаунте создан один MySQL-снимок; повторный снимок без проверки его состояния не создаётся.

Целевое локальное хранилище — `F:\jino`, обычные файлы, как ранее выбрал пользователь. В журнал попадают команды, безопасные идентификаторы, этапы, длительности, объёмы, контрольные суммы и коды ошибок. Логины, пароли, имена БД, cookies, токены, SQL и сырые авторизованные страницы не публикуются.

## Критерии результата

1. Действия выполняет команда `backupctl` с адаптером приложения, а не отдельный исследовательский скрипт.
2. Аккаунт, контейнер, снимок и файловый источник сопоставлены явно; неоднозначность останавливает выгрузку.
3. Перед экспортом проверены защищённый канал скачивания, каталог назначения и отсутствие конфликта с чужими файлами.
4. Экспорт использует конкретный снимок и явное назначение `/backups/…`; импорт SQL в production не выполняется.
5. После постановки задания приложение наблюдает его результат и не отправляет повторную мутацию при неопределённом ответе.
6. Полученные файлы проверены по размеру, SHA-256 и признакам полного SQL-дампа; отсутствие файла или SQL-проверки не выдаётся за успех.
7. Результат выгрузки БД отделён от полноты копии сайта и от теста восстановления приложения.
8. Соединения и временная авторизация закрыты; SQL и локальные результаты сохранены по прямому указанию пользователя. Удаление не выполняется.

## Итог живого теста

**Выгрузка дампов приложением проверена успешно на одном разрешённом аккаунте, запись 2 JSON.** Все 3 БД выбранного снимка экспортированы в `/backups/2026-11-10` и скачаны через защищённый HTTPS-файловый менеджер Jino. Вход на другие панельные аккаунты не выполнялся. Ничего на предоставленных ресурсах не удалялось.

Выбран снимок `2026-11-10`, созданный в предыдущем пилоте после единственного запроса в 16:19:52 UTC. Новый снимок при этом тесте не заказывался. UI показывает дату с точностью до дня; время запроса не выдаётся за точное время готового снимка. Экспорт SQL выполнен позже, в интервале 17:35–17:42 UTC. Таким образом, выгружено состояние выбранного снимка, а не заявлен новый снимок на момент скачивания.

### Команда фактической выгрузки и продолжения

```powershell
.venv\Scripts\backupctl.exe backup export-jino-db --file abw_sibds__server.json --mapping examples/jino-mapping.json --source-row 2 --destination F:\jino --idempotency-key panel-integration-2026-11-10 --reuse-snapshot 2026-11-10 --execute --plaintext --browser-channel chrome
```

Эту же команду использовали при продолжении после ошибок и при контрольной проверке. Ключ не менялся. В готовом состоянии она только читает и проверяет локальные SQL, записывая результат проверки в журнал; новый экспорт не выполняет.

### Что происходит при перебоях

- Перед серверным действием сохраняются исходный список каталога и состояние `SUBMITTING`. Неопределённый ответ переводит работу к сверке результата; повторной мутации вслепую нет.
- В данном живом тесте остановки после первого экспорта и после скачивания действительно пройдены с тем же ключом, без дублирования первого экспорта.
- Неполный SQL остаётся отдельной частью; следующая попытка скачивает тот же серверный файл с начала. Побайтовая докачка SQL через этот HTTPS-адаптер пока не реализована. Другой файловый workflow имеет собственные checkpoints.
- Полностью полученный файл повторно используется только после совпадения ожидаемого размера и проверки SQL. Предыдущая часть сохраняется, новая рабочая копия фиксируется отдельно.
- При остановке между финальным переименованием и записью результата журнал восстанавливается по заранее сохранённым размеру, хешу и проверке SQL. Этот случай проверен искусственным сбоем локально.
- Неоднозначный файл, чужое содержимое каталога, изменение UI, лимит или тайм-аут дают ошибку; их нельзя выдавать за успешный бэкап. После неопределённого результата ключ не следует менять, поскольку новый ключ означает другое задание.
- Принудительного отключения сети на реальном аккаунте не делали. Сетевой обрыв воспроизведён на синтетическом адаптере; живые остановки были вызваны строгими проверками размера и формата SQL.

### Границы результата

`DB_ONLY` означает успешную выгрузку всех БД **этого снимка аккаунта**. Привязки к отдельным клиентским сайтам, файлы сайтов, полный бэкап портфеля и работоспособность восстановленного приложения здесь не проверены. Прежние отказы FTPS не устранены; HTTP без TLS и отключение проверки сертификатов не применялись. Автоматическое создание нового снимка в этой команде и подключение её к `backup run --mode auto` пока отсутствуют. PostgreSQL и прочие аккаунты этим тестом не покрыты.

Три серверных SQL и локальные результаты намеренно сохранены (`KEEP_REMOTE`). `cleanup_verified: false` не скрывается; успешная очистка не заявляется. Публичные события: `.state/panel_jobs/panel-job-2afecaf265d1d9d1a21c059f.events.jsonl`; последний отчёт — одноимённый `.json`; приватное состояние — `.enc`.

### Команда первой живой инспекции

```powershell
.venv\Scripts\backupctl.exe backup export-jino-db --file abw_sibds__server.json --mapping examples/jino-mapping.json --source-row 2 --destination F:\jino --idempotency-key panel-integration-2026-11-10 --reuse-snapshot 2026-11-10 --execute --inspect-only --browser-channel chrome
```

Команда импортирует в локальный шифрованный провайдер только выбранный аккаунт и связанный профиль из той же исходной записи. Пароли не передаются в аргументах процесса. Авторизация живёт только в памяти браузерного контекста и не сохраняется в cookies-файл. Закрытие контекста входит в `finally` адаптера.

Журнал приложения находится в `.state/panel_jobs/`: публичные `.events.jsonl` и `.json` содержат только безопасные сведения; состояние переходов и приватные названия/пути хранятся зашифрованными в `.enc`. Запись `SUBMITTING` сохраняется **до** отправки операции. При потере ответа повторный запуск должен сверять фактический результат, а не отправлять второй экспорт.

### Окружение фактической проверки

Финальная локальная проверка: `.venv\Scripts\python.exe -m pytest -q` — **149 passed, 1 skipped** за 22,19 с. Пропущен необязательный отдельный нативный MySQL-тест; импорт реальных SQL в БД не выполнялся. `.venv\Scripts\python.exe -m compileall -q src` и `git diff --check` завершились успешно. Дополнительно проверен случай блокировки неожиданной мутации: публичный код `UI_CHANGED`, без повторного разрешения уже отправленного запроса.

Windows, Python 3.11, Playwright 1.51.0, `cryptography` 44.0.2, pytest 7.4.4; используется установленный Google Chrome в режиме headless. Зависимость браузерного адаптера объявлена отдельным extra `panel`. Отсутствие браузера или зависимостей не должно выдавать ложный результат теста; базовые команды импорта и справка работают без этого extra.
