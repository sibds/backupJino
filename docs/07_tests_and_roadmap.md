# Приёмочные тесты и план реализации

## Критерии приёмки

| ID | Проверка | Ожидаемый результат |
| --- | --- | --- |
| T01 | Импорт `abw_sibds__server.json` со схемой после утверждения mapping | Правильное число аккаунтов; значения секретов отсутствуют в отчётах; ошибочные строки явно перечислены. |
| T02 | Импорт 43 профилей FileZilla | Все профили распознаны либо отмечены как проблемные; недопустимо неверное автоматическое сопоставление. |
| T03 | Jino только с FTP без БД | Копия файлов с `FILES_ONLY`, предупреждение, отсутствие ложного `COMPLETE`. |
| T04 | Доступна панель Jino | Подтверждён новый снимок с датой и выгружены файлы и SQL. |
| T05 | Изменён интерфейс панели | `UI_CHANGED`; случайные действия и восстановление production не выполняются. |
| T06 | Обрыв FTPS/SFTP | Безопасный повтор/resume, проверка артефактов, нет дублирования задания. |
| T07 | MFA/CAPTCHA | Пауза для оператора, без попыток обхода защиты. |
| T08 | Повреждённый SQL-дамп | `INTEGRITY_FAILED`; результат не `COMPLETE`. |
| T09 | Захвачен доступ к хостингу | Ранее созданные внешние версии недоступны для удаления через аккаунт хостинга. |
| T10 | Изолированное восстановление | Дамп импортирован в тестовую БД, файлы развёрнуты, структура приложения проверена. |
| T11 | Прерывание процесса | Сессии закрыты, временные секреты и файлы удалены, корректный код ошибки. |
| T12 | Не удалось удалить одноразовый экспортёр | Критическое уведомление и зафиксированная необходимость ручного удаления. |

## Этапы разработки

### Этап 0 Техническое исследование

- Получить тестовый Jino-аккаунт и согласование владельца.
- Проверить текущий auth flow, MFA, создание свежего снимка, выгрузку SQL и файлов в `backups/`, передачу по FTPS/SFTP.
- Изучить фактическую структуру `abw_sibds__server.json` **без публикации секретов** и зафиксировать mapping.
- Уточнить состав сайтов, корневые директории и количество связанных БД.

**Результат:** работающий и безопасный прототип получения хотя бы одной полной копии, список ограничений и подтверждённых полей.

### Этап 1 MVP файлов и импорта

- `site_registry`, `secrets_provider`, импорт двух исходных форматов.
- Безопасные FTPS/SFTP, staging, список файлов, манифест.
- Загрузка шифрованного пакета во внешнее хранилище и проверка чтения.

**Результат:** проверенная файловая копия, детерминированные статусы и аудит.

### Этап 2 Полный бэкап

- Адаптер панели Jino с тестами и обработкой изменений UI.
- Адаптеры прямого MySQL и SSH; альтернативный PHP только по отдельному запросу.
- Проверка SQL и достоверного времени исходного снимка.

**Результат:** полный комплект файлов и БД на контрольном сайте.

### Этап 3 Эксплуатация

- Планировщик, ретраи, блокировки, ротация и уведомления.
- Отчёты об аномалиях и регулярные изолированные тесты восстановления.
- Правила хранения, аудит безопасности и процедуры обновления селекторов Jino.

**Результат:** сервис сохраняет и проверяет резервные копии без ручного контроля каждого шага.

### Этап 4 Управление портфелем

- Веб UI, роли, REST API, отчёты по клиентам и связь с агентом.
- Инциденты, история версий и контроль сроков последней успешной копии.

**Результат:** оператор управляет всеми сайтами через единый интерфейс.

## Вопросы для подтверждения

1. JSON получен и структурно исследован; требуется операторская проверка назначения полей и привязок. `sites.xml` требует корректного повторного экспорта из FileZilla: текущий XML синтаксически некорректен.
2. Какие из 37 Jino-профилей FileZilla актуальны? Нужно ли включать 6 других хостингов?
3. Какие CMS и число БД используются на сайтах? Где хранится конфигурация подключения?
4. У всех ли аккаунтов есть доступ к панели Jino? Используется ли двухфакторная авторизация?
5. Какое внешнее хранилище планируется и кто владеет ключами шифрования?
6. Нужен ли на первом шаге только ручной запуск или ежедневное расписание обязательно?
7. Какой объём данных, допустимый интервал резервирования, RPO/RTO для критичных проектов?

Ответы дополнят спецификацию без изменения основных контрактов.

## Локально реализованный этап

Доступны импорт, CLI, SQLite-реестр с отдельным провайдером секретов, FTPS/SFTP, файловый workflow, прямой MySQL-экспорт, проверка зашифрованных архивов и интервальное расписание. Команды: [README](../README.md); покрытие и ограничения: [локальная валидация](09_local_validation.md).

Дополнительно реализовано скачивание обычных файлов с сохранением прогресса, проверкой частичного префикса и продолжением после аварийного завершения процесса. На том этапе прошли 103 теста, 1 необязательный нативный MySQL-тест был пропущен. [Первый панельный пилот и отказы файлового прохода](10_download_and_panel_pilot.md) сохраняются как исторический результат.

Затем добавлена отдельная панельная выгрузка MySQL из существующего снимка. На одном разрешённом аккаунте приложение экспортировало и скачало все 3 БД, проверило структуру SQL, размер и SHA-256. Повторные запуски после ошибок не дублировали экспорт; готовый результат повторно проверен локально без входа. [Подробный журнал](11_database_export_integration.md). Это подтверждает SQL-часть T04, но полный T04 с файлами сайта и автоматическим созданием снимка ещё не закрыт. Сетевые обрывы и остановка после переименования проверены на синтетическом адаптере. Серверные SQL сохранены по прямому указанию пользователя.

Прохождение синтетических тестов не закрывает полный T04, реальные изменения UI/MFA (T05/T07), T09 (права реального внешнего хранилища), T10 (восстановление приложения и БД), T12 (PHP-экспортёр). Эти интеграции не реализованы или требуют отдельного разрешённого окружения. Обработка исключений и `KeyboardInterrupt` не подтверждает очистку после принудительного завершения процесса.
