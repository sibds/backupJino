# Безопасность и хранение резервных копий

Это требования целевой системы и ограничения локального прототипа. В текущем выбранном режиме копии в `F:\jino` сохраняются обычными файлами; шифрование архивов — отдельный workflow. S3/Object Lock, автоматическое удаление по retention и внешний notifier не реализованы. Исходный секретный JSON пока читается локальной панелью при запуске: не считайте его автоматически удалённым или полностью заменённым vault после импорта. Новые и изменённые через UI секреты хранятся отдельно в шифрованном vault; исходник не изменяется. [Текущие команды и ограничения](../README.md).

## Модель угроз

| Угроза | Требуемая защита |
| --- | --- |
| Компрометация всего аккаунта Jino | Копии хранятся вне Jino в отдельном контуре, куда аккаунт хостинга не имеет доступа. |
| Компрометация VPS с оркестратором | Права записи без удаления старых версий, отдельные ключи администрирования retention. |
| Перехват FTP-пароля | Только FTPS/SFTP с проверкой сертификата или host key; plaintext FTP запрещён в штатном режиме. |
| Кража файла `abw_sibds__server.json` | Безопасный одноразовый импорт, vault, запрет коммита файла в git и запрет на логирование его содержимого. |
| Кража FileZilla XML | Учесть, что base64 является обратимым кодированием; не считать сохранённые пароли защищёнными. |
| Подмена сайта до бэкапа | Несколько исторических версий, контроль изменений, сканирование и восстановление последней известной исправной. |
| Повреждение копии при передаче | SHA-256, проверка размера и чтения внешнего объекта, выборочный тест восстановления. |
| Временный PHP-экспортёр остался на сайте | TTL, одноразовая операция, обязательное удаление и критическое уведомление при неудаче. |
| Ошибка оператора в панели | Строгие проверки контекста; backup workflow не имеет права восстанавливать поверх production. |

## Секреты

В локальном прототипе провайдер секретов использует отдельный зашифрованный SQLite-файл; реестр содержит ссылки `secret_ref`. Это начальный адаптер, без разграничения прав промышленного vault. Защита каталогов и отдельная копия ключа являются обязанностью развёртывания. Подробнее: [ограничения локальной проверки](09_local_validation.md).

1. `abw_sibds__server.json` и FileZilla XML размещаются во временной защищённой области только на период импорта; в публичный репозиторий не помещаются.
2. Пароли, ключи и токены из импорта записываются в vault. В БД приложения — лишь `secret_ref`, метаданные и флаг проверки.
3. Зашифрованные/хэшированные значения в исходном дампе должны быть классифицированы отдельно. Если это необратимый хэш, восстановить пароль из него нельзя: требуется новый пароль или делегированный доступ.
4. Не передавать пароли как аргументы командной строки, query-параметры URL или текст логов.
5. После завершения job уничтожать временные сессии, cookies, файлы экспорта и рабочие секреты. Состояние браузера также считается секретом.
6. Сопоставление клиента/сайта и аккаунта подтверждает оператор. Один скомпрометированный сайт не должен давать доступ к другим.

**Рекомендуемые исключения для репозитория:** `abw_sibds__server.json`, `sites*.xml`, `.env`, `*.credentials.json`, `playwright/.auth/`, `staging/`, `backups/`. Отдельные правила поиска секретов — в CI.

## Защищённое внешнее хранилище

Минимальные требования:

- Не находится на том же аккаунте, у того же провайдера или в том же административном контуре, от которого защищаемся.
- Шифрование данных до загрузки; отдельно хранимые и восстанавливаемые ключи.
- Версионирование объектов и управление сроком хранения.
- Режим неизменяемости (например, S3 Object Lock или проверенный эквивалент) с ограниченным правом удаления.
- Отдельные бакеты/префиксы и политики по клиентам; журнал доступа.
- Проверка фактической доступности чтения записанного артефакта.

Для production рекомендуется принцип 3-2-1-1-0 как целевая политика: несколько копий, независимое хранение, одна неизменяемая копия, ноль необнаруженных ошибок проверки. Конкретное число копий и стоимость утверждаются после инвентаризации объёмов.

Если выбран Restic, необходимо проверить, как его операции `forget`/`prune` сочетаются с внешним Object Lock. Удаление и обслуживание репозитория должно выполняться **отдельными** правами, не доступными ежедневному backup-runner.

## Контроль полноты

**Файлы:** список путей, число объектов, размер, SHA-256 архивов, проверка распаковки, включение конфигурации и медиа, явный список исключений. Не выходить за пределы разрешённого FTP-корня по символическим ссылкам.

**База:** перечень всех БД данного сайта, тип/версия СУБД, размер, число таблиц и экспортный статус. Проверка синтаксического наличия SQL-инструкций не равна доказательству восстановления: нужен импорт в изолированную БД.

**Согласованность:** для Jino-снимка использовать время источника; для живого FTP + БД указывать `BEST_EFFORT`, если нет механизма единой точки времени. Для активных сайтов согласовать окна обслуживания или механизмы транзакционного/приложенческого снимка.

## Восстановление

Текущее исключение по прямому выбору пользователя: команды `download-servers` и `export-jino-db` сохраняют обычные файлы в `F:\jino`, а не зашифрованные архивы. Это отражается явно в манифесте и не заменяет целевое шифрованное внешнее хранилище. Для панельного теста действует `KEEP_REMOTE`: серверные SQL и локальные неудачные части остаются до нового указания пользователя. Секретные названия/пути журнала зашифрованы отдельно; cookies и токены существуют только в памяти закрываемой браузерной сессии. Передача SQL использует HTTPS с проверкой сертификата и токеном в заголовке, перенаправления запрещены. [Результат и границы проверки](11_database_export_integration.md).

1. Выбрать конкретный `job_id` и убедиться, что его артефакты доступны.
2. Развернуть файлы в изолированном окружении, восстановить БД в тестовый экземпляр.
3. Проверить связность конфигурации, наличие обязательных таблиц и запуск приложения (в пределах доступных тестов).
4. Сохранить `RestoreTest` и уведомить об ошибке.
5. Запрещать автоматический импорт дампа в исходную production-БД.

**Важно:** технически правильный бэкап уже заражённого сайта может содержать вредоносные изменения. Хранить версии, сравнивать их и проводить антивирусную проверку/аудит кода при признаках компрометации.
