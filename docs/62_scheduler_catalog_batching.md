# Повторное чтение справочника в планировщике

18 ноября: проверка текущих заданий показала ноль active_transfers при шести RUNNING. Стеки подтвердили ожидание передатчиков в очередях, а потоков обхода — общей блокировки DashboardManagement.progress. Планировщик в это время повторно читал и обрабатывал весь справочник через WorkPlans.list → catalog.get → catalog.all для каждого правила. Проверки и обход нельзя описывать как непрерывное скачивание новых байтов.

WorkPlans.list теперь получает один снимок справочника для всего списка правил. Проверки binding_revision, blocked и deleted сохранены. На действующих 40 правилах измерено: 0,4103 секунды на прежние отдельные обращения против 0,0163 секунды на новый список (примерно 25 раз). Это измерение операции чтения настроек, а не обещание такого же ускорения FTP.

Полный прогон: 530 passed, 1 skipped. Новый регрессионный тест проверяет одно чтение справочника при нескольких правилах.

Исправление установлено с технической паузой: ожидающие задания временно удержаны, активные работники получили pause через API. После фиксации checkpoint процесс заменён, исходные состояния очереди и правила восстановлены. Прежние workflow_key, части и ручные паузы сохранены; интервалы расписаний не менялись. Протокол — `.state/catalog-batching-deployment.json`.

После установки подтверждены новые FILE_DOWNLOAD и прирост 1324 байта в файловом задании строки 6. В контрольном срезе active_transfers снова равен нулю: основная работа — обход и проверка прежних копий. Это подтверждает отдельные передачи, но не непрерывную высокую скорость и не завершение полных копий. До установки за время наблюдения объём строки 1 вырос примерно на 87 МиБ; этот прирост не следует приписывать новой оптимизации.
