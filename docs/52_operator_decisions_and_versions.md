# Запросы решений и варианты копий

Указание оператора от 16 ноября: проблемы не должны молча завершать работу. В управляемой панели необработанный отказ становится запросом решения, а остальные задания продолжаются. При различающихся вариантах оператор предпочёл явный выбор вместо автоматической замены. Это уточняет прежнюю автоматическую замену собственного файла из [51](51_changed_source_refresh.md).

## Как это видно в панели

Общий блок «Нужно ваше решение» перечисляет сервер и вид работы. Ссылка открывает нужную вкладку карточки. Запрос и действия расположены постоянно видимо, включая вкладку БД: свёрнутые параметры задания их не скрывают.

Возможные состояния:

- Временная проблема обрабатывается существующими повторами с сообщением о времени продолжения.
- Конфликт файла показывает варианты сразу, пока остальные файлы ещё скачиваются. Такой запрос не меняет `RUNNING` и не мешает допуску очереди.
- Когда проблемную операцию продолжить нельзя, задание получает `WAITING_OPERATOR / ACTION_REQUIRED` и сохраняемый `operator_request`. Оно не занимает работника и не повторяет входы без решения. Корень, TLS, привязка и доступ остаются обязательными проверками.
- Пауза и остановка по кнопке оператора сохраняются. Запись решения по файлу не снимает ручную паузу. После выбора в ожидающем задании продолжение ставится автоматически с прежним ключом.

Запрос содержит идентификатор подтверждения, причину и допустимые действия. Повтор устаревшего подтверждения отклоняется. Запрос сохраняется после перезапуска; существующие незавершённые управляемые отказы также получают запросы. Исторические отчёты/журналы не переписываются. CLI и архивный workflow не меняют свои статусы отказов.

## Варианты файла

Карточка показывает исходные пути, размеры, даты и результат сравнения содержимого. Оператор выбирает:

1. **Новая папка версии** — проверенный серверный вариант сохраняется в `files/versions/<дата-идентификатор>/<исходный путь>`, старая копия остаётся. Манифест и checkpoint содержат соответствие серверного и локального путей.
2. **Обновить существующую** — кандидат проверяется до замены. Прежние проверенные байты сохраняются в истории, сторонние локальные изменения не перезаписываются без отдельного решения.
3. **Оставить локальную** — серверный вариант пропускается по явному решению. Это не выдаётся за полную копию изменившегося источника.

Проверенная совпавшая копия используется без создания новой версии. Утверждение оператора «размер вырос — обновить, дата новее — новая версия» служит ориентиром сравнения; последующее уточнение требует спросить о различающихся вариантах, поэтому решение автоматически не применяется.

## `REMOTE_DESTINATION_EXISTS`

На Jino это означает неизвестные текущему БД-заданию файлы в каталоге экспорта, а не обязательно совпадение имени нового SQL. Вместо молчаливого `FAILED` карточка предлагает прочитать список существующих SQL, затем выбрать действия.

Чтение списка выполняется заданием управляемой очереди с прежними ограничениями входов. Найденные имена, пути и метаданные сохраняются в зашифрованной SQLite-таблице, с привязкой к серверу, ревизии и заданию. Общий API их не содержит; карточка получает только приватное представление без сырого токена удалённого пути.

Оператор сравнивает размер и дату удалённого файла с последней проверенной локальной копией, затем выбирает новую папку версии, обновление копии текущего задания или сохранение локальной. Если имя SQL не сопоставлено с известной БД, требуется явно выбрать БД из текущей привязки. Произвольный путь или неизвестный alias принять нельзя. Повторное назначение двух кандидатов одной БД в одном подтверждении отклоняется. Другие форматы автоматически не импортируются.

Перед скачиванием и после него проверяются тип, путь, размер и время SQL; незавершённые задачи экспорта Jino не выдаются за стабильный файл. После скачивания проверяются SQL, размер и SHA-256. Повторный импорт того же принятого кандидата использует проверенную копию. При обновлении существующей копии прежние SQL сохраняются в `history/`; при выборе новой папки используются `versions/<идентификатор>/databases/…`.

Найденный SQL не доказывает дату снимка только своим расположением. Поэтому сохраняется `source_snapshot_verified: false`, дата исходного снимка показывается как неподтверждённая, отдельно от даты файла и скачивания. Такой SQL не переиспользуется как доказанный экспорт конкретного снимка Jino. Имена БД не попадают в общий API, отчёты и публичные журналы. Никакие найденные файлы на Jino не удаляются, новый серверный экспорт поверх них автоматически не отправляется.

## API и проверки

`POST /api/tasks/<id>/decision` принимает `request_id` и одно из действий, разрешённых текущим запросом: повтор, чтение SQL, применение выбора SQL, подтверждение восстановленного доступа либо новой привязки. `POST …/conflict` дополнен `new_version`. У изменения привязки есть явное подтверждение нового задания; прежние части не присваиваются другому источнику.

Проверки: полный прогон **462 passed, 1 skipped**, дополнительные целевые проверки — **23 passed**, отдельно **17 passed** после проверки инициализации чтения SQL; JS — **31 passed**. Локальный Schannel вне песочницы прошёл реальные FTPS-тесты; песочница давала `SEC_E_NO_CREDENTIALS`, это не результат проверки Jino. Chrome на **1440/1000/800/390**, только синтетические данные; два принятых POST при двойных кликах, ошибок JavaScript нет, горизонтального переполнения нет. Отдельно проверены 22 запроса: три видны сразу, остальные раскрываются. Снимки — `.impeccable/review/operator-decisions-*.png`, сценарий — `scripts/check_operator_decisions_ui.py`.

Протокол установки — `.state/operator-decisions-deployment.json`. Перед следующими живыми действиями сверять фактическое состояние, сохранять ключи и части и не прерывать активный серверный экспорт БД.

Применено 16 ноября: кооперативно сохранены пять файловых работников, затем сверены все 84 прежних задания/ключа и настройки 40 правил. Прежние актуальные отказы преобразованы в запросы; история не очищена. Для БД строки 3 поставлено только чтение существующих SQL с прежним ключом; контрольный статус `WAITING_RATE_LIMIT`, `inspection_pending: true`. Ближайший допуск на момент проверки — 16 ноября 09:41 по Омску, фактический старт зависит от общей очереди. Варианты не выбирались, SQL и копии без решения оператора не перезаписывались. Файловые задания продолжают работу.
