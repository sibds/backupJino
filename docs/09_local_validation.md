## Запуск проверок

Для уже установленного окружения Windows:

```powershell
New-Item -ItemType Directory -Force -Path .test-tmp | Out-Null
.venv\Scripts\python.exe -m pytest -q --basetemp .test-tmp/validation
```

`--basetemp` должен указывать на отдельный каталог тестов: pytest очищает его перед запуском. Не задавайте путь с исходными файлами, ключами, архивами или рабочим состоянием. Параллельные запуски должны использовать разные каталоги.

Тесты используют синтетические записи JSON/XML, временные ключи и файловый источник с тем же контрактом, что у FTPS/SFTP. Проверки CLI выполняются отдельными Python-процессами; файловый workflow проверяется со скрытыми файлами, пустыми каталогами и контрольными суммами. Дополнительно запускается настоящий локальный FTPS-сервер: проверяются TLS управляющего и файлового каналов и отказ при недоверенном сертификате. Реальные клиентские доступы тестам не нужны.

Отдельный интеграционный тест создаёт временный MySQL-сервер с собственным каталогом данных и сертификатом, на случайном loopback-порту. Проверены MySQL 8.0.22, экспорт `mysqldump` с проверкой TLS, полный зашифрованный пакет, независимое извлечение, импорт SQL обратно в тестовую БД и восстановление контрольной строки. Служба MySQL и существующие БД не используются. Процесс тестового сервера завершается после испытания.

Запуск интеграционного теста при установленных `mysqld`, `mysql`, `mysqldump`:

```powershell
$env:JINO_RUN_NATIVE_MYSQL_TEST = '1'
.venv\Scripts\python.exe -m pytest tests/test_native_mysql.py -q --basetemp .test-tmp/native-mysql-validation
Remove-Item Env:\JINO_RUN_NATIVE_MYSQL_TEST
```

Без этой переменной тест MySQL пропускается. На исходной проверке 10 ноября `paramiko` не был установлен; SFTP-адаптер был подготовлен, но не испытан на живом сервере. На том этапе входов в клиентские аккаунты, сохранения реальных паролей в рабочий реестр и резервного копирования клиентских данных не выполнялось. Более поздние живые проверки перечислены в начале документа и не подтверждаются этим историческим прогоном.

Проверяемые свойства:

- `dry-run` доступен без инициализации и не создаёт реестр или хранилище секретов; импорт без карты полей возвращает только структуру.
- `--confirm` и `--dry-run` взаимоисключающие; подтверждённый импорт требует явной карты JSON с разными обязательными колонками.
- Ошибки JSON/XML и аргументов CLI не содержат переданных значений и traceback.
- Реестр профилей хранит `secret_ref`; зашифрованные значения находятся в отдельном SQLite-файле. Изменения реестра и локального хранилища секретов участвуют в одной транзакции через SQLite ATTACH.
- Неоднозначные аккаунты не перезаписываются; повторный импорт неизменённых кандидатов идемпотентен. Привязка клиента, сайта, файлового профиля и удалённого корня выполняется явно.
- Для неподтверждённого сайта запуск блокируется до сети. `site validate` проверяет локальную конфигурацию и явно возвращает `network_checked: false`.
- Для одного сайта разрешено только одно активное задание; повторный `idempotency_key` возвращает прежнее задание.
- Файлы без обязательных дампов БД дают `FILES_ONLY`; код возврата CLI для частичного результата — `2`, для ошибки — `1`, для успешной команды — `0`.
- `COMPLETE` требует явного подтверждения состава БД, всех успешных экспортов, проверенных файлов и успешного чтения зашифрованного архива. Ошибка одной из нескольких БД сохраняет доступные данные со статусом `FILES_ONLY` и перечнем ошибок по псевдонимам БД.
- Обрыв передачи ограничивает число повторов; resume допускается только при неизменившихся доступных метаданных. Изменение источника, символическая ссылка и опасный путь прекращают копирование.
- Повреждение зашифрованного архива выявляется до выдачи расшифрованного результата; извлечение не перезаписывает существующий каталог.
- При штатной ошибке и `KeyboardInterrupt` закрывается файловый источник и очищается staging; ошибка очистки становится `CLEANUP_FAILED` и не выдаётся за успех.

## Ограничения доказательств

Пользователь выбрал локальное хранение с настраиваемым путём. Приложение не перезаписывает архивы; старые объекты не удаляются. Выбор отдельного пути сам по себе не доказывает Object Lock или отсутствие у процесса прав удаления на уровне ОС.

Локальное шифрованное хранилище секретов не предоставляет разграничения доступа и аудита промышленного vault. На Windows права `chmod` не заменяют ACL: каталог состояния, staging и ключи должны принадлежать только оператору или сервисному аккаунту. Ключ хранится вне каталога архивов и нуждается в отдельной защищённой копии.

Восстановление файлов в новый каталог не является проверкой восстановления клиентской БД или запуска приложения. Интеграционный тест импорта SQL подтверждает цикл на синтетической БД; `application_restore_tested: false` остаётся явным результатом команд продукта.

Контекстные менеджеры обрабатывают обычные исключения и прерывание с очисткой Python. Принудительное завершение процесса, отключение питания, восстановление зависших заданий и автоматическая очистка оставшегося staging требуют отдельного эксплуатационного этапа.

Изначальные локальные тесты не проверяют авторизацию Jino, MFA, серверные возможности FTPS/SFTP, полноту состава сайтов и доступ к реальным БД. Последующие отдельно разрешённые живые действия и их границы вынесены в [отчёт панельного пилота](10_download_and_panel_pilot.md); не смешивайте их с доказательствами синтетических тестов.
