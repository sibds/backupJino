# PostgreSQL в панельных выгрузках

17 ноября 2026 года в код добавлена поддержка PostgreSQL через существующие снимки Jino. Основание — явное сообщение оператора о PostgreSQL в строке 47 и сохранённый публичный код панели `.state/panel-research/filemanager-3c8e4dd6e87b6d14.js`: в нём присутствуют getBackupPostgreSQLDatabases, restorePostgreSQLBackup и отдельный выбор типа снимка. Это наблюдаемый внутренний контракт, не обещание стабильного публичного API.

Официальная [справка Jino](https://jino.ru/spravka/hosting/sql.html) подтверждает поддержку MySQL и PostgreSQL. Она не подтверждает успешную выгрузку конкретного аккаунта. Формат стандартного текстового экспорта описан в [документации pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html).

## Поведение

- Управляемая выгрузка «все БД» читает доступные снимки обоих типов в одном входе в панель, затем выполняет отдельные журнальные экспорты последовательно. Второй вход для PostgreSQL не нужен.
- Последняя дата выбирается отдельно для MySQL и PostgreSQL. При продолжении даты закрепляются в database_snapshots задания. Прежний snapshot_date и workflow_key MySQL сохраняют смысл и совместимость.
- Выборочные aliases проверяются по объединению обоих типов до экспорта. Групповые интервальные расписания по-прежнему используют aliases; группа может включать оба типа. Сами расписания реальным клиентам этим изменением не включались.
- MySQL сохраняет прежние aliases и ключи. PostgreSQL получает отдельное пространство aliases, snapshot_ref и panel-job, поэтому одноимённая БД не присваивается другому типу. В шифрованном каталоге хранится engine, в карточке показаны MySQL/PostgreSQL. Старые записи без engine считаются MySQL.
- Для PostgreSQL разрешена только соответствующая операция restorePostgreSQLBackup с ранее наблюдаемыми параметрами, привязкой аккаунта и проверкой каталога экспорта. Это копирование SQL в backups, не восстановление данных приложения в действующую БД. Новые снимки и удаление чужих экспортов не добавлены.
- Проверяется стандартный текстовый PostgreSQL SQL-dump: заголовок, завершение, размер и SHA-256 локального файла. HTML, оборванный SQL, MySQL вместо PostgreSQL и бинарный custom-архив PGDMP не считаются проверенными дампами. Проверка не выполняет SQL и не заменяет тест восстановления. Поддержка PostgreSQL через pg_dump напрямую, SSH, custom/tar/directory-архивы и gzip этим изменением не добавлена.
- Проверенные копии повторно проверяются и используются без нового заказа экспорта; принадлежность собственных remote-экспортов восстанавливается и для повторно используемой копии. Отказ целостности одного типа не мешает обработке другого; общий результат сохраняет отказ и успешные артефакты.
- Публичный результат объединённого задания содержит engine_results с отдельными датами и job_id, общий счётчик и артефакты. При разных датах общий source_snapshot_date остаётся неизвестным; их нельзя выдавать за один синхронный снимок. История обоих журналов импортируется в приватный каталог после запуска до работников.

Имена клиентских БД остаются в шифрованном каталоге и приватной карточке. Общие API, журналы и отчёты не получают их перечень. Сохранены проверки TLS, путей, привязки, владения файлами, ручные управляющие действия и общий допуск входов панели.

## CLI

У backup export-jino-db появился необязательный `--database-engine mysql|postgresql`, по умолчанию mysql. Например, проверка синтетического плана без входа:

```powershell
backupctl backup export-jino-db --file SOURCE.json --mapping MAPPING.json --source-row ROW --destination F:\jino --idempotency-key pg-request --reuse-snapshot YYYY-MM-DD --database-engine postgresql --dry-run
```

Обычные ограничения CLI сохранены: реальная операция требует execute и подтверждения plaintext, сам CLI не охвачен допуском управляемой очереди. Не запускать его параллельно управляемой очереди для обхода допуска.
