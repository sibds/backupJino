# Массовое скачивание и панельный пилот — 10 ноября 2026 года

## Разрешённый объём

Пользователь разрешил чтение файлов всех серверов из `abw_sibds__server.json`, выбрал обычные файлы и папки в `F:\jino`, отдельно для каждого сервера. Для панели разрешён только первый аккаунт с пригодными доступами: штатный вход, одна свежая копия БД и её скачивание, без восстановления сайта. Это разрешение не распространяется на массовое создание снимков в остальных аккаунтах.

## Результат файлового прохода

Из 56 записей 54 прошли локальную проверку FTP-полей. У записей 48 и 55 FTP-параметры отсутствуют. Все 54 пригодных профиля проверены по FTPS с включённой проверкой сертификата и защитой канала данных:

| Результат | Записей |
| --- | ---: |
| `TLS_CERTIFICATE_INVALID` | 21 |
| `CONNECTION_FAILED` | 31 |
| `AUTH_OR_ROOT_FAILED` | 2 |
| Успешно скачанные серверы | 0 |

Для первого сервера отдельно подтверждён отказ проверки сертификата на этапе AUTH TLS, код проверки 10 (просроченный сертификат в проверяемой цепочке). На этом этапе учётные данные ещё не передавались. Причины остальных ошибок TLS не приравниваются автоматически к этой причине. `CONNECTION_FAILED` не доказывает неверность пароля, а `AUTH_OR_ROOT_FAILED` не различает отказ авторизации и недоступный корень.

Файлы сайтов не получены. В целевом каталоге созданы только принадлежащие этому запуску папки и служебные данные для продолжения. Итоговый обезличенный отчёт: `F:\jino\download-dcc4059959a9fe22683715ca.json`. Исходные JSON и XML не изменялись. TLS-проверка не отключалась; перехода на plaintext FTP не было.

Для продолжения нужны рабочие параметры защищённого файлового доступа: действительный и доверенный сертификат FTPS либо разрешённый SFTP с проверенным ключом сервера. Штатный вход в веб-панель не подтверждает работоспособность отдельного FTP-профиля.

## Подтверждённое в панели Jino

На первом однозначном кандидате панельного импорта — **запись 2** исходного JSON — Playwright выполнил штатную авторизацию. Неоднозначные аккаунты импортёр исключает из кандидатов. В новом интерфейсе наблюдались переходы «Хостинг» → единственный контейнер → «Бэкапы» и «Доступ к файлам». Явное соответствие FTP-профиля и аккаунта панели осталось неподтверждённым: обнаружение строки логина на странице само по себе не доказывает привязку.

Форма «Создать бэкап» предоставляет выбор типа «Файлы» или «MySQL». Для пилота выбран только MySQL. Запрос создания отправлен ровно один раз с предварительной записью состояния операции. До запроса сохранён список существующих копий; после состояния создания появился один новый элемент MySQL, для которого стало доступно меню действий. Другие снимки не создавались и не удалялись.

В меню нового элемента наблюдался пункт «Восстановить базу MySQL». Проверка текущего интерфейса и реально загруженного публичного кода показала, что пункт открывает форму выбора даты и БД. В форме явно указано: **SQL-дамп будет скопирован в `/backups/<дата>`**. Открытие формы выполнило чтение списка БД; отправка команды выгрузки и импорт данных в production не выполнялись.

Выгрузка SQL остановлена до запуска: FTP-профиль записи 2 получил `TLS_CERTIFICATE_INVALID`; явная привязка к панели также требует подтверждения. Сейчас нельзя завершить скачивание и гарантированно очистить созданный временный SQL. Провайдерский снимок MySQL оставлен в панели как намеренно созданная резервная копия. Он не является скачанным и проверенным SQL-артефактом.

Эта проверка подтверждает основной путь из SDD: создание копии на стороне Jino и подготовка SQL в файловом каталоге без внешнего подключения к MySQL. Она **не подтверждает** готовность полного панельного адаптера, успешную генерацию выгружаемого SQL-файла, его скачивание, полноту всех БД сайта, точное время исходного снимка или восстановимость приложения. `backup run --mode auto` пока использует реализованный прямой MySQL-адаптер при наличии подтверждённой конфигурации; панельный сценарий ещё не подключён к оркестратору.

Не переносить в будущий адаптер слепой клик по тексту «Восстановить». Обязательны проверка выбранного аккаунта, контейнера, конкретного нового снимка, БД и явного назначения `/backups/…`. При потере ответа сначала сверять состояние уже отправленного задания; повторное создание снимка без такой проверки запрещено.

Браузерные контексты закрыты; временные cookies/state и копии авторизованных страниц, которые сохранялись локально только зашифрованными, удалены. Минимальный отчёт и журнал единственного запроса оставлены в защищённой `.state/`; они не содержат паролей, cookies, имён БД или сырых страниц.

## Сбои и продолжение файлов

`backup download-servers` сохраняет готовые файлы и подтверждённые части в отдельном каталоге запуска. Повтор команды с тем же `--batch-id` продолжает незавершённую копию. Перед использованием части проверяются размер, время изменения источника и SHA-256 локального префикса. При отсутствии времени изменения неполный файл начинается заново. Готовые файлы не перезаписываются при изменении источника: фиксируется `SOURCE_CHANGED`, для новой версии нужен новый `--batch-id`.

Запись данных синхронизируется перед фиксацией длины в SQLite. Аварийное завершение отдельного процесса проверено тестом: 8 МиБ были подтверждены, следующий хвост не подтверждён; после перезапуска хвост отброшен и передача продолжена с границы 8 МиБ. Блокировки снимаются ОС при завершении процесса. Автоматический запуск после загрузки Windows не настраивался: требуется повтор команды.

Общий результат локальной проверки: **103 теста прошли, 1 необязательный нативный MySQL-тест пропущен**. Проверены также возобновление после сетевого исключения, отказ при повреждении сохранённой части, обнаружение изменения готового файла, разделение серверов и продолжение обработки после ошибки одного сервера.

## Следующий этап панельного адаптера

После восстановления защищённого файлового доступа нужно завершить на том же разрешённом аккаунте выгрузку всех требуемых БД из конкретного снимка, дождаться окончания задачи, скачать SQL, проверить артефакты и убрать только временные файлы этой операции. Затем выделить проверенные действия в адаптер и добавить тесты изменения UI, неоднозначного результата отправки, тайм-аута и потери сессии. Массовые панельные операции требуют отдельного разрешения.
