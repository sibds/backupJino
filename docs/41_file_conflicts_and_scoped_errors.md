# Конфликты файлов и границы остановки задания

## Правила сравнения

Управляемые FTPS/SFTP-задания могут изолировать конфликт одного объекта, продолжая остальную выгрузку. Неразрешённый конфликт включается в `files.errors` и даёт `PARTIAL`, а не полную копию. При строгом обходе коллизия остаётся фатальной. HTTPS-адаптер этим изменением не расширен.

Для совпавших имён файлов серверный вариант сначала скачивается в принадлежащий заданию каталог `.jino-progress/conflicts`, с отдельным checkpoint и проверками источника до и после передачи. Сравнивается SHA-256 содержимого, а не только размер и дата. Для первого сравнения необходимо прочитать серверные байты; это не обещание отсутствия сетевого скачивания. Совпавший по содержимому второй серверный путь записывается в `files.duplicates` с `source_path`, `stored_path` и SHA-256. Дополнительный физический файл не создаётся. Это соответствие необходимо учитывать при восстановлении имён; автоматическое восстановление приложения не реализовано.

Для того же исходного пути приложение автоматически обновляет более новую серверную версию только при известной сравнимой дате и подтверждённом по прежнему SHA-256 владении старой копией. Предыдущие байты сохраняются в `.jino-progress/preserved`. Более новая дата не означает одинаковое содержимое. Неизвестные даты, более старая серверная версия и изменённый оператором локальный файл требуют решения. Разные серверные пути, отличающиеся регистром, не заменяют друг друга автоматически только из-за даты.

## Решение оператора

На вкладке файлов карточки есть блок «Конфликты файлов»: оба исходных пути, размеры, даты и результат сравнения содержимого. Доступны «Сохранить оба», «Пропустить серверный», а для обычного конфликта локального файла — «Использовать серверный». У различающихся типов/каталогов содержимое не считается сравнённым. Пропуск по решению пользователя сохраняет `PARTIAL`.

Решение сохраняется в прежнем задании; остальные файлы и серверы не ждут ответа. После завершения текущего прохода оператор продолжает это же задание. Создавать новый ключ не нужно. Разрешение относится к конкретным путям, хешам и метаданным; изменившийся конфликт потребует нового решения. Ручные паузы и остановки сохраняют прежнюю семантику.

При сохранении обоих вариантов используется отличимый локальный суффикс. SQLite checkpoint хранит отображение `locations`; в манифесте `items[].path` указывает реально сохранённый артефакт, `source_path` — исходный серверный путь, если он отличается. Для каталогов отображение применяется к потомкам. Чужой локальный файл не перезаписывается: сохранённые рядом объекты описываются в `retained_local` и проверяются при валидации дерева. Кандидаты, предыдущие версии и части автоматически не удаляются.

Приватный `GET /api/servers/{row}` дополнен `conflict_events`, отбираемыми до LIMIT 500. Общий API состояния не получает клиентские пути из этих событий. `POST /api/tasks/{id}/conflict` принимает `conflict_id` и `decision`: `keep_both`, `keep_local`, `use_remote`. Проверяются тип задания, принадлежность события этому заданию, текущая привязка и блокировка сервера. Ответ `apply_on_resume` сообщает, что отдельного перезапуска/остановки работающего задания эта команда не вызывает.

## Какие другие ошибки можно изолировать

| Ошибка | Область и поведение |
| --- | --- |
| `REMOTE_PATH_COLLISION` | В управляемой выгрузке — сравнение/вопрос по объекту вместо остановки обхода; строгий режим сохранён. |
| `LOCAL_DESTINATION_CONFLICT` | Конфликт файла с каталогом или локальным содержимым передаётся оператору; остальные объекты продолжаются. |
| `LOCAL_FILE_CHANGED` | Управляемый FTPS передаёт объект на отдельное сравнение. Локальные изменения не перезаписываются автоматически. Для остальных исполнителей остаётся прежняя пофайловая ошибка. |
| `SOURCE_CHANGED` | Уже обрабатывается как пофайловая ошибка при `continue_on_error`; нестабильная передача не считается копией. Изменившаяся между запусками известная версия может быть обновлена по правилам выше. Изменение во время самой передачи не маскируется. |
| `TRANSFER_DENIED` | Уже изолируется в пределах файла: журнал, `files.errors`, `PARTIAL`. Отказ входа или доступа к корню — отдельная блокирующая ошибка. |
| `REMOTE_DIRECTORY_UNAVAILABLE` | Уже изолируется для подкаталога; пропускается всё недоступное поддерево, результат `PARTIAL`. Недоступность корня остаётся фатальной. |
| `LOCAL_PROGRESS_INVALID` | Уже изолируется как пофайловая ошибка; повреждённая подтверждённая часть сохраняется. Добавлено понятное пояснение. Автоматическое уничтожение/сброс части не реализованы. |
| `REMOTE_NAME_UNSUPPORTED`, `REMOTE_TYPE_UNSUPPORTED` | Существующие разрешённые пропуски; журнал, манифест и `PARTIAL`. |
| Временные сетевые сбои | Прежние пять операционных переподключений, затем плановое продолжение того же файлового задания. Постоянный обрыв не следует повторять для каждого следующего файла без ограничения нагрузки. |

Следует останавливать задание при ошибке TLS/host key, неверных доступах, неподтверждённой привязке, выходе за корень, небезопасном структурном пути, неизвестном типе удалённого объекта, нехватке места и общих лимитах. `INTERNAL_ERROR` требует диагностики и не превращается в безусловный пропуск. `UI_CHANGED`, CAPTCHA/MFA и непроверенный дамп БД также не обходятся. Файловая изоляция не означает автоматического повтора экспорта БД.

## Проверки и применение

Сценарии сравнения, обновления с сохранением старой версии, вопроса при одинаковом размере и разном содержимом, независимой передачи остальных файлов, решений и повторного использования checkpoint проверяются в `tests/test_file_conflicts.py` и `tests/test_conflict_decisions.py`. Синтетический браузерный сценарий — `scripts/check_file_conflicts.py`, ширины 1440/390, выбор не останавливает RUNNING. Внешние запросы блокируются, в том числе вставляемые установленным антивирусом. Клиентские аккаунты этими тестами не используются.

Перед применением backend проверяются активные задания; части и идентификаторы сохраняются. Итог проверок и установки дописывается после выполнения, а не предполагается из наличия кода.

Проверка 14 ноября: полный прогон **373 passed, 1 skipped**, 74,97 с; после дополнительного сценария изменения источника — **40 целевых тестов прошли**. JS-регрессии — **22 passed**. Новый браузерный сценарий прошёл на 1440/390 без ошибок страницы, две операции решения не остановили RUNNING. Прежние карточки, таблица и навигация дополнительно проверены на 1440/1000/800/390, без ошибок страницы. Первые FTPS-отказы внутри песочницы повторно проверены вне её сетевого ограничения; синтетический TLS-прогон — 12 passed.

Установка: `.state/file-conflicts-final-deployment.json`, фаза `RESTORED`: пять активных и 21 ожидающее задание восстановлены, сохранены все 26 ID очереди, новых заданий нет. Перед этим в тот же план возвращены пять последних файловых заданий с прежним `REMOTE_PATH_COLLISION`, с сохранением их ID; прочие постоянные ошибки автоматически не повторялись. Живая GET-проверка подтвердила установленный `conflict_events` и JavaScript блока решений. Это подтверждает установку и сохранение очереди, а не завершение всех деревьев или живую проверку каждой возможной коллизии.
